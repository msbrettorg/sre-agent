Source and calculation

Billing profile: not loaded.

Live path: browser → localhost bridge → Azure Billing, Cost Management, and Kusto REST APIs. Azure CLI authentication stays on the server. The browser does not directly invoke the hosted SRE Agent connector.

Subscription used to resolve the billing profile: 8e9e64d9-d158-4638-a087-f2c60bff9e66. The report covers the linked billing profile, not just that subscription.

Actual utilization: Microsoft.CostManagement/benefitUtilizationSummaries, version 2025-03-01. Completed UTC days only. The lowest utilization is not a commitment-weighted portfolio average.

Purchased inventory and metadata: Microsoft.Billing/billingAccounts/savingsPlans, version 2024-04-01, filtered to the verified billing profile. Active means Succeeded, benefits started, and not expired. This billing-scoped API uses existing billing access and doesn't require access to the separate Billing Benefits resource.

Observed coverage: Costs() and Prices() in ftk-sitecore-eus.eastus.kusto.windows.net / Hub. Match the billing profile, meter, currency, and effective dates. Savings-plan price records determine eligibility. SQL Server license meters belong to database plans, not compute plans. Divide used savings-plan ContractedCost by eligible non-reserved usage ContractedCost; purchases, unused commitment, and Spot are excluded. Billable unmatched or ambiguous meters fail explicitly, not as zero coverage.

Recommendations: Microsoft.CostManagement/benefitRecommendations, version 2025-03-01, expanded scenario details, Shared scope, Last30Days, P1Y/P3Y. Current coverage follows the selected plan type and currency.

Model calculations use exact Azure-evaluated options. Monthly equivalents multiply each observed-window cost by 730 / totalHours. They assume the historical usage pattern continues; they are not forecasts or contract quotes. Net savings already include unused commitment, so wastage is not subtracted again.

Do not add overlapping one-year and three-year recommendations. Compute and database scenarios are separate eligible-usage pools. No monetary savings are inferred from actual utilization. Refresh re-queries live sources; concurrent requests share only work already in flight, not saved results.

No purchases, Azure configuration changes, saved-result fallbacks, synthetic data, or browser access tokens.
